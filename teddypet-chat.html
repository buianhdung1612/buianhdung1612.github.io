TEDDYPET · REAL-TIME SUPPORT CHAT

Chat that survives disconnects

A separate customer-to-staff chat service with idempotent sends, ordered messages and replicas behind Nginx.

IMPLEMENTED · COVERED BY TESTS (2026-11-15)Socket.IORedisOutboxNestJS
TL;DR
Problem

Sockets drop, tabs retry and instances restart, yet no message may be lost, duplicated or reordered.

Approach

Database commit before ACK, unique client message ids, per-conversation sequence numbers, a transactional outbox and Redis fan-out.

Proof

Unit specs plus two integration specs: the Nest module against PostgreSQL, and two Socket.IO replicas over Redis.

01Problem

A support chat feels trivial until the network misbehaves. A customer on mobile loses signal mid-send, a browser retries, a server instance restarts, and staff must lose access the moment their session is revoked. Naive designs duplicate messages, reorder them, or acknowledge a message that never reached the database.

02Constraints
  • A message is acknowledged only after it is committed to the database.
  • Sending the same message twice must not create two rows.
  • Clients that missed events must be able to catch up deterministically.
  • Chat must stay separate from commerce data and use its own database.
  • AI helpers must not receive raw personal data.
03Design

  1. A separate service and database

    Core owns identity. Chat verifies a 5-minute JWT issued by Core (audience chat-service) whose scopes — chat:self, chat:reply, chat:read_all, chat:assign — are checked in the service. Chat never connects to Core's database.

  2. Commit first, then ACK

    The database commit comes before a successful acknowledgement. (senderId, clientMessageId) is unique, which makes sending idempotent. seq orders messages per conversation and changeVersion orders edits.

  3. Sockets are best effort

    Real-time push is not the source of truth. Clients catch up with afterSeq and changedAfter, so a missed event costs one request, not data.

  4. Transactional outbox

    Side effects are enqueued in the same transaction as the message by the outbox service, and their handlers are idempotent.

  5. Scale out

    The compose file runs two replicas behind Nginx. A Redis adapter fans out Socket.IO events; Redis is also used for rate limits, spam counters and presence, never as the source of truth.

  6. Staff routing and safety

    Conversations are auto-assigned to online staff, spam triggers an automatic lock, a 10-day retention job deletes old data, and attachments are checked by magic bytes and downloaded through HMAC-signed links. Core can revoke a session in chat immediately.

  7. AI assist with redaction

    Reply suggestions, rewrite, summary and sentiment use the Claude API after personal data is masked by redact(). Customers never see the sentiment value.

  8. Operability

    Single-line JSON logs carry a correlation id, and Prometheus metrics use low-cardinality labels.

05Verification

What is shown

  • Text and attachment messages, infinite-scroll history, presence push, typing and unread counts per conversation.
  • Auto-assignment with history, open / closed / locked status and automatic spam locks, ratings.
  • Message and conversation deletion with file cleanup, and the 10-day retention job.
  • AI suggestions, rewrite, summary and sentiment (the model call is mocked in tests).
  • Immediate session revocation from Core, Prometheus metrics and a CI workflow.

Not verified / not built

  • Real Claude API calls: the tests mock the model.
  • A full local-e2e.cjs run together with Core, and the chat UI in a browser.
  • Backup, TLS, alert rules and failover for the compose deployment.
  • Not built: message search, notifications outside the chat, object storage and antivirus scanning for attachments, and queued message fan-out.
06Trade-offs

Best-effort sockets, reliable catch-up

It is simpler and cheaper than guaranteeing delivery over a socket, and the sequence numbers make recovery deterministic.

Outbox means at-least-once

Handlers must be idempotent, which is extra care in exchange for never losing a side effect.

Attachments on a shared volume

A shared filesystem volume is easy to run but is not object storage, so scaling beyond one host would need a change.

A database per service

No cross-service joins; identity crosses the boundary only through short-lived signed tokens.
