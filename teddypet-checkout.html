TEDDYPET · CHECKOUT & INVENTORY

Checkout that never oversells

How TeddyPet keeps stock, coupons and orders consistent when requests race, retry or arrive twice.

IMPLEMENTED · TEST CASES IN REPOPostgreSQLPrismaIdempotencySerializable
TL;DR
Problem

Two buyers click “buy” on the last unit, a client retries after a lost response, an admin saves a product from a stale form.

Approach

Idempotency keys, one atomic conditional stock update per SKU, a serializable transaction with bounded retry, and release-once markers.

Proof

PostgreSQL integration tests: 100 distinct keys fight for 10 units and exactly 10 orders succeed.

01Problem

A naive checkout reads the stock, checks it, then writes the new value. Under concurrency that sequence can sell the same unit twice, create two orders for one click, or lose a reservation when an admin saves an old product form. Mobile clients also retry when a response is lost, so the same purchase can arrive more than once.

02Constraints
  • Never sell more units than exist, even when requests for the last unit race.
  • The same Idempotency-Key with the same payload returns the same order; the same key with a different payload is rejected with 409.
  • Stock reservation, coupon use, order, order items and the first payment attempt commit together or not at all.
  • Money is an integer in VND and is recalculated on the backend, never trusted from the client.
03Design

  1. One key, one purchase

    The scope is checkout:user:<id>. The key and the canonical request body are hashed with SHA-256 and stored with the order in the same transaction. A pg_advisory_xact_lock on that scope and hash serializes concurrent requests that carry the same key.

  2. Reserve with one atomic statement

    Stock is taken with updateMany({ where: { id, stock: { gte: quantity } }, data: { stock: { decrement: quantity } } }). If the affected row count is not exactly 1, the request is rejected with a conflict. There is no read-then-write window.

  3. Serializable transactions with bounded retry

    The transaction runs at Serializable isolation. Serialization failures and deadlocks (P2034, P2002, SQLSTATE 40001 / 40P01) are retried up to five attempts with exponential backoff and jitter. Only database work runs inside the callback so a rolled-back attempt is safe to repeat.

  4. Release exactly once

    Cancelling or expiring an order claims stockReleasedAt with a conditional update under a row lock (SELECT … FOR UPDATE on the order). Stock and the coupon redemption are restored only by the request that wins the claim, and an audit row records it.

  5. Stale admin edits cannot erase reservations

    Admin stock edits carry the snapshot they started from. A stale snapshot is rejected and the whole product update rolls back, so a checkout that reserved stock in the meantime is preserved.

04Evidence in code
Reserving stock: a single conditional updateLinh_BE/src/routes/orders/orders.service.ts
for (const sku of skus) {
  const quantity = requested.get(sku.id)!.quantity;
  const reserved = await tx.sKU.updateMany({
    where: { id: sku.id, deleted: false, stock: { gte: quantity } },
    data: { stock: { decrement: quantity } },
  });
  if (reserved.count !== 1)
    throw new ConflictException(/* stock changed, retry */);
}

05Verification

What is shown

  • 100 distinct keys compete for 10 units: exactly 10 orders are accepted, 90 are conflicts, stock ends at 0, and each saved order has one item and one payment attempt.
  • Concurrent requests with the same key commit one order, one stock movement and one initial payment attempt.
  • The same key with a different payload is serialized and the mismatched intent is never recorded.
  • A failure while creating the payment attempt rolls back stock, coupon, order items and the idempotency record.
  • The last coupon use is reserved once and restored once, even on repeated cancellation.
  • A stale admin stock edit is rejected and rolled back; of two admins editing from the same snapshot only one succeeds.

Not verified / not built

  • The tests exist in the repository. Their results were not re-run when this page was written.
  • No throughput or latency figure is claimed. The scenarios prove correctness, not capacity.
  • Not yet exercised on production-like infrastructure or across several API instances.
06Trade-offs

Serializable isolation costs throughput

Serializable plus retries is the simplest way to stay correct, but a very hot SKU will see retries and conflicts. The system returns a clear conflict instead of overselling.

Held stock can sit idle

Stock stays reserved until the payment deadline (15 minutes by default, plus up to 5 to verify). Unpaid orders therefore hold inventory for a while.

Uncertain payments never auto-release stock

If a provider result is unknown, the order goes to review after 24 hours and only an admin can release it. This avoids selling stock that may already be paid.

Everything lives in PostgreSQL

There is no Redis data cache in front of the catalogue. That keeps one source of truth at the cost of read load on the database.
