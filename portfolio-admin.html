TEDDYPET · ADMIN APPLICATION

Store Operations Console

A focused workspace for maintaining the catalog, stock, and customer-facing operations behind the storefront.

Detailed note, written in English. The Vietnamese case study summarises this page. Storefront & Admin → · Storefront & Admin →
01 / OPERATIONS GOAL

Give staff a reliable view of store data.

The admin app brings product and SKU management, categories, brands, orders, reviews, blog content, and settings into one console. It uses the same commerce API and domain rules as the customer storefront, with access controls for privileged actions.

02 / DATA GRID DESIGN

What React Query owns here

TanStack Query manages remote server state. Filter controls own the current selection; query keys and requests use the same normalized parameters.

Filter statestatus · stock · search · page
Query key + requestsame filters define cache and API input
API + databaseaggregate stock, then paginate

01 Cache identity matches the request

The product list uses ['products', queryParams]. Search, status, stock, page, and page size affect the result, so normalized request parameters define both the key and the API request. Different filter states cannot accidentally share a cached page.

02 Keep the table steady while paging

keepPreviousData keeps the last page visible while the next request runs. The table avoids flashing empty between pages, while loading state communicates that new results are on the way.

03 Refresh the views affected by a write

Product create, update, delete, restore, and permanent delete invalidate the products query family. Updating one product also refreshes its detail key. Review writes refresh the product and customer review views that depend on them.

04 Filter inventory before pagination

Stock status is based on summed SKU quantities: zero is out of stock, 1–20 is low stock, and above 20 is in stock. The API applies this before slicing pages, so page counts match the filtered result set.

Scale trade-off: SKU totals are aggregated in the database, while matching product IDs are paginated by the API. For a much larger catalog, move stock aggregation and page selection into one SQL query or maintain a stock summary.

CACHE POLICY30s stale time

Recent results can be reused during short navigation between screens.

FAILURE POLICY1 query retry

A transient request failure gets one retry without an unbounded loop.

WRITE STRATEGYServer-confirmed + invalidate

Paginated lists take the API response as truth, then refresh affected queries.

03 / KIẾN TRÚC ADMIN

Module theo nghiệp vụ, form dùng lại theo phạm vi.

Cùng quy ước với Client: App Router giữ route; mỗi feature Admin sở hữu màn hình, hook, schema và API adapter; phần thực sự dùng chung nằm ngoài feature.

01 Form tạo/sửa dùng chung

Product, Brand và Coupon dùng một form cho mỗi cặp route tạo/sửa. Form Product giữ chung validation, variant/SKU và bộ chọn ảnh; dữ liệu sửa được nạp theo ID.

02 Ranh giới được kiểm tra

Admin không import feature Client. UI và hook của feature không gọi HTTP trực tiếp; adapter giữ endpoint và contract. Architecture check chạy trước build cùng TypeScript và OpenAPI contract check.

04 / ENGINEERING DECISIONS

Keep list behavior predictable.

01

Separate server state from UI state. The query cache owns API results; filter controls own the user’s current selection.

02

Use resource-prefix invalidation. One product mutation can affect multiple filtered pages, so related active views refresh together.

03

Let the API define stock filtering. Filtering only the loaded page would produce incomplete results and incorrect totals.

04

Keep the data path inspectable. Query key, request parameters, endpoint, and database filter follow the same filter model.

INTERVIEW WALKTHROUGH

“The query key fully describes the list request, mutations invalidate the views they can change, and pagination keeps previous data visible during transitions. Stock filtering belongs in the API because filtering one page in the browser would misrepresent both the result set and its total.”
