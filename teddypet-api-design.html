TEDDYPET · API DESIGN

An API with a contract

Validated inputs, predictable lists and one OpenAPI file that the frontend types are generated from.

IMPLEMENTEDNestJSZodOpenAPIPagination
TL;DR
Problem

Backend and frontend drift apart, list endpoints behave differently, and invalid input reaches business code.

Approach

Zod DTOs, allowlisted filters and sorts with deterministic order, integer money, and OpenAPI exported then turned into frontend types.

Proof

The frontend build checks the generated contract; typecheck, API version and architecture checks passed on 2026-11-06.

01Problem

On a shop this size, many endpoints are written over months by one person. Without a contract, list pages paginate differently, sorting is unstable between pages, floating-point money creeps in, and the frontend guesses response shapes.

02Constraints
  • Every list uses the same pagination contract and a stable order.
  • Only allowlisted fields can be filtered or sorted, so no query can hit an unindexed column.
  • Money is an integer in VND everywhere.
  • A backend change that breaks the frontend must fail a build, not production.
03Design

  1. Validation at the edge

    Controllers use Zod DTOs through createZodDto and a ZodValidationPipe declared per controller.

  2. Predictable lists

    List endpoints use page / pageSize with shared limits, resource-specific filter and sort allowlists, and deterministic ordering. Price filtering and sorting use a lowest selling price kept up to date transactionally across active SKUs.

  3. Route and permission convention

    Routes live under admin/* and client/*; a permission guard matches method and path against the role's permission rows.

  4. Contract first, types generated

    npm run openapi:export writes openapi-v1.json; the frontend generates its API types from it and api-contract:check verifies them as part of the build.

  5. Idempotency as a shared tool

    The checkout idempotency helper is a shared service, so other write endpoints can reuse the same key and payload semantics.

05Verification

What is shown

  • Pagination, allowlists and deterministic ordering are shared across list endpoints.
  • Frontend architecture, API version, API contract and tsc checks all passed on 2026-11-06.
  • Twelve API design decisions are written up in the detailed notes below.

Not verified / not built

  • The cart and wishlist controllers do not use ZodValidationPipe, so limits such as quantity 1–99 are not enforced there yet.
  • Rate limiting exists only for authentication. A general rate limiter and helmet were not found, and are on the list to close before a public launch.
  • The admin notifications page calls an endpoint the backend does not serve.
06Trade-offs

Per-controller pipes

Declaring the validation pipe on each controller is explicit, but a new controller that forgets it silently skips validation. A global pipe would remove that risk.

Allowlists limit flexibility

Fixed filter and sort fields keep queries safe and indexed, at the cost of a new field needing a small code change.

Contract drift is caught late in the chain

Generating types catches breakage at frontend build time, not at backend commit time.
