TeddyPet E-commerce

A connected commerce product: a customer storefront, an admin console, a shared domain API, a media service and a real-time support chat. The engineering focus is reliable checkout, payment state and secure sessions.

01 / Architecture

One product, connected responsibilities.

The storefront and admin console share a Next.js app and call the commerce API. Chat and media are separate services with their own data.

APPLICATIONNext.jsStorefront · Admin console
↓ same-origin rewrites  ·  direct REST + WebSocket to chat ↓
CORE · :3000Commerce APINestJS · Prisma
MEDIA · :3001File ManagerUpload · Sharp · derivatives
CHAT · :3002Chat ServiceSocket.IO · outbox · 2 replicas
↓ Prisma · Redis · Mongo ↓
DATAPostgreSQL + RedisOrders · stock · sessions
DATAMongoDBMedia metadata (replica set)
DATAPostgreSQL + RedisChat only, never shared with Core

This is a responsibility map, not a deployment topology. Services talk through signed tokens and HTTP; no message broker is used, and background jobs run in-process.

04 / Verification

Evidence before claims.

What the repository shows

  • PostgreSQL integration scenarios for checkout races, rollbacks, stale admin edits and payment callback races.
  • Chat service unit and integration specs, including two Socket.IO replicas over Redis.
  • Frontend architecture, API contract and type checks that fail the build.

Not verified yet

  • A real VNPay Sandbox transaction through a public HTTPS callback.
  • Any throughput or latency figure; none is claimed.
  • Test results were not re-run when these pages were written.
  • Known gaps before a public launch: general rate limiting and helmet, tests for the media service, server-side admin route protection.
