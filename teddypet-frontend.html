TEDDYPET · STOREFRONT & ADMIN

A frontend with boundaries

One Next.js app serving the storefront and the admin console, with architecture rules that fail the build.

IMPLEMENTED · STATIC CHECKS PASSED (2026-11-06)Next.jsReactTanStack QueryZustand
TL;DR
Problem

A large frontend rots when features import each other and components call the network directly.

Approach

Two apps in one repo with enforced import rules, API adapters per feature, generated API types and a deliberate rendering strategy.

Proof

Architecture, API version, API contract and tsc checks all passed on 2026-11-06; 85 route pages.

01Problem

A storefront plus an admin console quickly grows into hundreds of files. Without rules, admin code leaks into the shopper bundle, components fetch data on their own, and the cache behaves unpredictably.

02Constraints
  • Storefront and admin code must never import each other.
  • Components and pages must not call the network directly; requests belong in an API adapter.
  • Public pages must be fast and fresh without hitting the API on every view.
  • Checkout must recover when a response is lost.
03Design

  1. Boundaries enforced by a script

    scripts/check-architecture.mjs runs before every build: no imports between client/ and admin/, shared/ cannot import either, and feature pages, components and hooks cannot call fetch or the Axios clients.

  2. Server state and local state

    TanStack Query holds server data; Zustand holds session and local UI state. The access token is not persisted and refresh is serialized with navigator.locks.

  3. Deliberate rendering

    The home page uses ISR, shop and blog lists render per request, and cart, checkout and admin use client-side queries. Public data comes from server-only fetches that use the Next.js Data Cache; Core calls a secured revalidation endpoint to expire cache tags.

  4. Contract-generated types

    API types are generated from the backend OpenAPI file, so a breaking backend change fails the frontend check.

  5. Checkout recovery

    The checkout stores its idempotency key and payload in the session so a lost response can be recovered by replaying the same request.

  6. Content tools for the shop owner

    A page-layout editor reorders and toggles blocks, previews drafts, publishes and refreshes the public cache. Product reviews go through moderation. The UI is available in English and Vietnamese.

05Verification

What is shown

  • 85 route pages across the storefront and admin console.
  • Cart merge on login, checkout with idempotency recovery, VNPay result page, admin CRUD features, page-layout editor and the chat panel.
  • Architecture, API version, API contract and tsc checks all passed on 2026-11-06.

Not verified / not built

  • Only five test files exist, all for logic. There are no component or browser end-to-end tests.
  • Admin route protection runs on the client; there is no server-side middleware yet. The API still enforces permissions.
  • No Dockerfile or CI yet (output: 'standalone' is already set).
  • Two known mismatches with the backend: the admin notifications page and the folder-delete call.
06Trade-offs

One repo, two apps

Shared tooling and types are simple, but the boundary has to be policed by the script rather than by separate packages.

Client-side admin guard

Fast to build, but the UI guard is cosmetic. Real protection is the API permission guard.

Generated types

They remove drift, but force a regeneration step after every API change.
