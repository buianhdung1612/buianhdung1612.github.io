TEDDYPET · AUTHENTICATION & SESSIONS

Sessions you can revoke

Short-lived access tokens, rotating refresh sessions, MFA and abuse limits, designed so logout means logout.

IMPLEMENTEDJWTRefresh rotationTOTP MFARedis
TL;DR
Problem

Stolen or replayed tokens, sessions that outlive a revoke, and one user table serving shoppers and admins.

Approach

15-minute access JWT, 7-day refresh JWT rotated once inside a transaction, session checked in the database on every request.

Proof

Design documented as an ADR; auth integration tests run on a disposable PostgreSQL (not re-run for this page).

01Problem

A JWT that is valid until it expires cannot be revoked, and a refresh token that can be replayed turns one leak into permanent access. The shop also has two audiences, customers and admins, that share a user account but must not share a session.

02Constraints
  • Logout, device revoke or role change must stop the next request, not wait for token expiry.
  • A reused refresh token must be detected and punished.
  • Customer and admin sessions must be independent, with their own cookies, audiences and endpoints.
  • Login abuse limits must hold across several API instances.
03Design

  1. Two tokens, two lifetimes

    The access JWT lives 15 minutes and carries issuer, auth mode and audience. The refresh JWT lives 7 days; only its SHA-256 hash is stored in PostgreSQL and the token travels in an HttpOnly cookie. A session also has an absolute 30-day limit that rotation cannot extend.

  2. Rotate once, detect reuse

    A refresh token is rotated exactly once inside a database transaction. If an already-used token appears again, every refresh token of that device is revoked.

  3. Check the session on every request

    The JWT guard loads the active session from the database each time, so logout or revocation takes effect immediately. A permission guard then matches the HTTP method and route against the role's permission rows.

  4. One user table, separate session modes

    Customer and admin sessions have their own endpoints, token stores, audiences and cookies, so one logout never affects the other. The ADR records why a second identity system was not worth the extra moving parts.

  5. Abuse and MFA

    Failed-login counters are shared through Redis and keyed by hashed IP and normalized email. TOTP codes are accepted once per time window across instances; the secret is stored with AES-256-GCM. Enabling or disabling MFA revokes all sessions.

  6. Browser side

    The access token is not persisted. Refresh runs through Web Locks so several tabs do not refresh at once, and cookie requests are checked against the allowed origins and reject cross-site fetches.

05Verification

What is shown

  • Session design, rotation, reuse detection and revocation are implemented as described above.
  • A dedicated integration suite (npm run test:auth:postgres) targets a disposable PostgreSQL and refuses any other database.
  • Password recovery, OAuth (Google and Facebook) and TOTP MFA are implemented in code.

Not verified / not built

  • The auth tests were not re-run for this page, and sign-in against the live Google and Facebook providers is not evidenced here.
  • Admin MFA enforcement is controlled by ADMIN_MFA_REQUIRED and is only meant to be switched on after every admin has enrolled.
  • Admin route checks in the Next.js app run client-side. The API enforces permissions, but there is no server-side route middleware yet.
06Trade-offs

A database read per request

Checking the session each time makes revocation immediate, at the price of one lookup on every authenticated call.

Shared user table

Fewer moving parts than two identity systems, but the code must keep the mode boundaries consistent and migrate frontend and backend together.

Future identity provider

If admin and storefront ever split into separate domains, the ADR points to a dedicated OAuth/OIDC provider with mandatory admin MFA.
