TEDDYPET · PAYMENTS & FULFILMENT

Payments that don't guess

VNPay and GHN integrated around verified callbacks, reconciliation and explicit recovery states.

IMPLEMENTED / TESTED (MOCKED PROVIDER)VNPayGHNReconciliationWorkers
TL;DR
Problem

A provider result can arrive late, twice, never, or after the customer cancelled.

Approach

Separate Order, Payment and Shipping state; verify every callback; reconcile with QueryDR; provider calls stay outside database transactions.

Proof

Integration scenarios for concurrent IPNs, IPN racing QueryDR, tampered IPNs and late payment after cancel (provider mocked).

01Problem

Payment results are not reliable messages. The IPN may be delivered twice, delayed beyond the order deadline, or lost entirely; the browser return URL can be forged or closed early. If the system guesses, it either ships unpaid orders or loses money that really arrived.

02Constraints
  • Only a verified result (signature, merchant, amount and attempt) may change payment state.
  • IPN and QueryDR must converge on one outcome without double-settling.
  • Money that arrives after cancellation must be recorded, not silently reopened or ignored.
  • Calls to VNPay and GHN must not run inside a database transaction.
03Design

  1. Three separate states

    Order, Payment and Shipping are tracked independently. COD orders are created UNPAID and are never treated as collected at creation or on delivery.

  2. One attempt per try

    Each VNPay try is a PaymentAttempt with its own txnRef. A failed, still-valid attempt can be retried on the same order; retries do not extend the deadline.

  3. Verify, then settle

    The IPN checks signature, merchant, amount and attempt. The Return URL only sends the browser to a page that reads status from the backend. IPN and QueryDR share settleSuccess and settleFailure, so a success arriving through both paths is settled once.

  4. Reconcile instead of waiting

    When an IPN is lost, QueryDR asks VNPay for the truth. New orders use QueryDR before cancel; the broader reconciliation switch stays off by design.

  5. Unknown stays unknown

    An uncertain result never releases stock automatically. After 24 hours it goes to review and only an admin can release it. Late money after cancellation is recorded and flagged, without reopening the order or creating a shipment.

  6. Fulfilment behind a gate

    An admin confirms the order (stock still held, no payment review, VNPay must be PAID). A worker then claims the order conditionally and calls GHN outside the transaction, retrying with the same client_order_code.

05Verification

What is shown

  • Concurrent signed IPNs are deduplicated and record one financial transition.
  • A concurrent IPN and QueryDR success settle only once.
  • A tampered IPN is rejected without writing financial evidence.
  • A signed IPN after customer cancel keeps the order cancelled and the stock released, and records the money.
  • Expiration serializes against a late payment and never releases stock twice.
  • After a provider network error the payment stays unresolved, then recovers on retry.

Not verified / not built

  • These scenarios run against a mocked provider. A real VNPay Sandbox transaction through a public HTTPS callback has not been evidenced yet; the planned verification file records the checklist.
  • Refunds are manual: an admin records money sent outside the system. VNPay's refund API is not used.
  • No throughput or latency figure is claimed.
06Trade-offs

Slower, but never wrong

Holding stock past the deadline so a late signed IPN can settle a live order costs inventory time, and avoids selling goods that were already paid for.

Manual refunds

Keeping refunds as a manual record avoids a half-built automatic flow, and leaves a real gap for later.

In-process workers

Background jobs use in-process cron (@nestjs/schedule) instead of a message broker, which keeps the stack small but ties job claiming to conditional database updates.
