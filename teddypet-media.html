TEDDYPET · MEDIA SERVICE

Uploads behind a ticket

A self-hosted media service with single-use upload tickets, file-type verification and image derivatives.

IMPLEMENTED · NO AUTOMATED TESTSNestJSMongoDBSharpUpload tickets
TL;DR
Problem

Public uploads attract oversized files, disguised file types and replayed requests.

Approach

Hashed single-use tickets bound to user, name, type and size; MIME allowlist plus magic-byte check; derivatives generated with Sharp.

Proof

Implemented and documented. There are no automated tests yet, and this page says so.

01Problem

Letting users upload files is where many apps get hurt: a renamed executable, a gigantic body streamed before any check, or one upload request replayed many times.

02Constraints
  • A ticket must be consumed before the server accepts the request body.
  • The real file type is decided from the bytes, not the filename.
  • Large originals must not be served directly to shoppers.
  • File bytes stay on disk and metadata in a database.
03Design

  1. Upload tickets

    A ticket is stored hashed, expires after 10 minutes and is bound to the user, file name, type and size. A guard reserves the single-use ticket before Multer accepts the body.

  2. Verify the file, not the name

    Allowed types are JPEG, PNG, WebP, GIF, MP4, WebM, MP3, M4A, WAV, OGG and PDF, checked against a MIME allowlist and magic bytes.

  3. Derivatives

    Sharp produces WebP, thumbnail and blur versions so pages load small images and not the original.

  4. Storage split

    Bytes live on the filesystem, metadata (Folder, MediaAsset, UploadTicket) in MongoDB. Deletes are soft, so records carry deleted, deletedAt and deletedBy.

  5. Shared token trust

    The service verifies Core access tokens with the same secret and a dedicated audience.

05Verification

What is shown

  • Ticket issue and upload, magic-byte checks, WebP / thumbnail / blur derivatives.
  • File listing, rename and soft delete, folder create, rename and recursive delete.
  • A liveness endpoint and a hardened Dockerfile and compose file.

Not verified / not built

  • No automated tests, lint or CI for this service.
  • Some folder routes do not register as documented (stacked route decorators register only the top path).
  • Any valid Core token, including a customer's, can request an upload ticket; library routes are limited to the super admin.
  • Not built: upload rate limits, per-user quotas, private or authenticated media delivery, garbage collection of soft-deleted files, and database or disk checks in the health endpoint.
06Trade-offs

Self-hosted filesystem

Cheap and simple to start, but it is not object storage, so a multi-host setup needs rework.

Soft deletes keep bytes

Safe and recoverable, but disk usage only grows until a cleanup job exists.

Honest gap

This is the least-tested part of the platform. It is listed here so the gaps are visible before they matter.
