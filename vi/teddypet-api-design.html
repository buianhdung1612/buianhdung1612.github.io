TEDDYPET · THIẾT KẾ API

API có hợp đồng rõ ràng

Đầu vào được kiểm tra, danh sách dự đoán được, và một file OpenAPI để sinh type cho frontend.

IMPLEMENTEDNestJSZodOpenAPIPagination
TL;DR
Vấn đề

Backend và frontend lệch nhau, các endpoint danh sách hành xử khác nhau, đầu vào sai lọt vào code nghiệp vụ.

Cách giải

Zod DTO, filter và sort theo allowlist với thứ tự xác định, tiền là số nguyên, OpenAPI được xuất rồi sinh type cho frontend.

Bằng chứng

Build frontend kiểm tra contract sinh ra; typecheck, API version và architecture check đều pass ngày 2026-11-06.

01Vấn đề

Với một shop cỡ này, nhiều endpoint được viết dần qua nhiều tháng bởi một người. Không có hợp đồng, các trang danh sách phân trang khác nhau, sắp xếp không ổn định giữa các trang, tiền dạng số thực len vào, và frontend phải đoán hình dạng response.

02Ràng buộc
  • Mọi danh sách dùng cùng một hợp đồng phân trang và thứ tự ổn định.
  • Chỉ field trong allowlist mới được lọc hoặc sắp xếp, nên không query nào đụng cột chưa có index.
  • Tiền luôn là số nguyên VND.
  • Thay đổi backend làm hỏng frontend phải làm hỏng build, không phải hỏng production.
03Thiết kế

  1. Kiểm tra ở biên

    Controller dùng Zod DTO qua createZodDto và một ZodValidationPipe khai báo trên từng controller.

  2. Danh sách dự đoán được

    Endpoint danh sách dùng page / pageSize với giới hạn chung, allowlist filter và sort theo từng resource, và thứ tự xác định. Lọc và sắp xếp theo giá dùng giá bán thấp nhất được cập nhật trong transaction trên các SKU đang bán.

  3. Quy ước route và quyền

    Route nằm dưới admin/* và client/*; permission guard đối chiếu method và path với các dòng quyền của vai trò.

  4. Contract trước, type được sinh ra

    npm run openapi:export ghi openapi-v1.json; frontend sinh type API từ file đó và api-contract:check kiểm tra trong lúc build.

  5. Idempotency là công cụ dùng chung

    Helper idempotency của checkout là service dùng chung, nên các endpoint ghi khác có thể dùng lại cùng ngữ nghĩa key và payload.

04Bằng chứng trong code
  • Linh_BE/src/shared/api-contract/pagination/Giới hạn phân trang và metadata response dùng chung
  • Linh_BE/docs/API_QUERY_DESIGN.mdHợp đồng danh sách và ví dụ
  • Linh_BE/docs/API_GOVERNANCE.mdQuy tắc quản trị API
  • Linh_BE/openapi/openapi-v1.jsonContract đã xuất
  • Linh_FE/src/shared/api-contracts/generated.tsType sinh từ contract

Đường dẫn tính từ thư mục gốc của repo TeddyPet.

05Kiểm chứng

Đã thể hiện

  • Phân trang, allowlist và thứ tự xác định được dùng chung giữa các endpoint danh sách.
  • Kiểm tra kiến trúc frontend, API version, API contract và tsc đều pass ngày 2026-11-06.
  • Mười hai quyết định thiết kế API được viết chi tiết ở phần ghi chú bên dưới.

Chưa kiểm chứng / chưa có

  • Controller cart và wishlist chưa dùng ZodValidationPipe, nên giới hạn như số lượng 1–99 chưa được ép ở đó.
  • Rate limit hiện chỉ có cho xác thực. Chưa thấy rate limiter chung và helmet; đây là việc cần đóng trước khi ra mắt công khai.
  • Trang thông báo của admin gọi một endpoint mà backend chưa phục vụ.
06Đánh đổi

Pipe khai báo theo từng controller

Khai báo pipe trên từng controller thì tường minh, nhưng controller mới quên khai báo sẽ âm thầm bỏ qua kiểm tra. Pipe toàn cục sẽ loại rủi ro này.

Allowlist làm giảm linh hoạt

Field filter và sort cố định giữ query an toàn và có index, đổi lại thêm field mới cần sửa code nhỏ.

Lệch contract bị bắt khá muộn

Sinh type bắt lỗi ở lúc build frontend, không phải lúc commit backend.
